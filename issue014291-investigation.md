I have investigated the cause of the unexpected line break in specs::issues::deno::issue014291.


  The issue is a "nested look-ahead trap" in dprint-core that interacts with the PossibleNewLine signals generated by dprint-plugin-typescript. Although the lineWidth is 120, the printer decides to break after the assignment operator = because of how speculative printing handles nested line groups.

  Sequence of Operations


  I have added numbered comments (1. to 8.) in the code to indicate the order of operations. You can follow them in src/generation/generate.rs and dprint-crates/core/src/formatting/printer.rs.


   1. Entry (generate.rs:9430): The assignment const id = ... begins. It pushes an ifAboveWidth condition.
   2. Assignment Break Point (generate.rs:9445): The ifAboveWidth condition checks if we've moved past the start of the line by more than indent_width (2). At const id = , we have (col 16 vs start col 6). This resolves to true and pushes a PossibleNewLine at column 17.
   3. Speculative Pass Start (generate.rs:2005): The expression is a complex BinExpr (??) containing a ternary (? :). This triggers an is_multiple_lines look-ahead in dprint-core.
   4. Speculation (printer.rs:755): dprint-core starts a speculative pass to see if the whole expression fits on one line. During this pass, it skips paths of nested conditions that are not yet resolved (like the ternary branches).
   5. Line Growth (printer.rs:826): Even with branches skipped, the combination of the long ternary test, the array, and the right side of the ?? causes the line to grow.
   6. Width Failure (printer.rs:826): During speculation, the printer hits the 120-character limit at the string 'data'.
   7. Group Trap (printer.rs:826): The printer looks for the most recent PossibleNewLine to break at. There are more specific break points inside the ternary, but they are at a deeper new_line_group_depth. dprint-core's logic prevents nested groups from overwriting the "parent" group's break point during
      width-triggered restoration.
   8. Incorrect Restoration (printer.rs:407): The printer restores to the only available "shallow" PossibleNewLine—the one after id = at column 17. It writes a newline there, which now "proves" that the expression is multi-line, locking in the bad layout.
